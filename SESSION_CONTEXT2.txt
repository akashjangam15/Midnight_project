5. THE CONTRACT — contracts/counter.compact
════════════════════════════════════════════════════════════════
PUBLIC ledger state (all three are on chain, readable by anyone):
  export ledger count: Uint<32>;               // running total
  export ledger updateCount: Uint<32>;         // successful increment() calls
  export ledger publishedMessage: Opaque<"string">;  // empty until disclosed

PRIVATE witnesses (declarations; implementations in src/witnesses.ts):
  witness privateStep(): Uint<32>;      // magnitude of each increment
  witness privateMessage(): Opaque<"string">;  // the counter's secret note

Circuits (3):
  increment()      → const step = privateStep(); assert(step > 0);
                     total = count + step; assert(total <= 4294967295);
                     count = disclose(total as Uint<32>);
                     updateCount = disclose((updateCount + 1) as Uint<32>);
  publishMessage() → publishedMessage = disclose(privateMessage());
  reset()          → count = 0; updateCount = 0;   (no witness, discloses nothing)

Exactly TWO disclose() calls exist — the privacy story is greppable.
The top-of-file comment block covers public vs private, why disclose() is the
authoritative crossing point, and why only the SUM of steps is published.

COMPILE FIX WORTH REMEMBERING: the first compile failed with
  "counter.compact line 75 char 9: expected right-hand side of = to have type
   Uint<32> but received Uint<0..8589934591>"
because Uint<32> + Uint<32> widens to 33 bits in Compact's range analysis.
Rule of thumb: any addition of two bounded Uints does NOT fit back into the
narrower width. Fixed with an explicit bound assert plus `as Uint<32>`.

6. TESTS — tests/counter.test.ts (5 passing, ~4s, no network)
════════════════════════════════════════════════════════════════
Run: npm test   (script: `tsx --test tests/counter.test.ts`)
Last result: tests 5 / pass 5 / fail 0.
Also: npx tsc --noEmit → clean.

  1. increment() adds the private step to the public count        (circuit logic)
  2. increment() refuses a non-positive private step              (the real
     on-chain assert path; also asserts no partial state was left)
  3. publishMessage() discloses the note, reset() clears only the public
     counters, private state survives reset()                     (state transitions)
  4. private inputs are never exposed in the public ledger state  (privacy)
  5. private state is JSON-serializable and fits Uint<32>         (deploy hygiene)

Test 4 is the meat: it asserts (a) Object.keys(ledger) is exactly the three
declared public fields, (b) the secret note's raw bytes are ABSENT from the
encoded public state before publishMessage() and PRESENT after, and (c) the
private step's own Uint<32> little-endian cell encoding never appears in the
public state even though its sum does.

How the harness works (no wallet needed): new Contract(witnesses) →
createConstructorContext(createCounterPrivateState(step, note), sampleUserAddress())
→ contract.initialState(...) → createCircuitContext(sampleContractAddress(),
initial.currentZswapLocalState, initial.currentContractState,
initial.currentPrivateState) → carry `res.context` forward per call →
ledger(ctx.currentQueryContext.state) to read public state.

8. GOTCHAS / THINGS THAT WILL BITE AGAIN
════════════════════════════════════════════════════════════════
- bigint IN PRIVATE STATE IS A DEPLOY-TIME TRAP. The Midnight.js private-state
  provider JSON.stringify()s private state (verified in
  @midnight-ntwrk/midnight-js-level-private-state-provider/dist/index.cjs →
  JSON.stringify(payload)), and JSON.stringify throws on BigInt. So
  CounterPrivateState.step is a `number`, converted via BigInt() inside the
  witness. A bigint there fails AFTER sync, not at compile time. Test 5
  guards this locally.
- Deploying is not upgrading. The address derives from the contract's initial
  state, so editing counter.compact and redeploying gives a NEW address; the
  old instance keeps its last state forever. Midnight's Contract
  Maintenance Authority (opt-in, threshold committee that can swap verifier
  keys) is NOT used here — this contract is frozen.
- npm run deploy OVERWRITES deployments.preview.address in
  .midnight-state.json. Write the current address down before redeploying:
  799afe68b3353f26ec9103fce6c9b3a67a85952ee8cf9e59134ce5662b4eb718
- A redeploy also starts with a fresh local private state — set it before
  calling any circuit (COUNTER_STEP / COUNTER_MESSAGE at deploy time, or
  option 1/2 in the CLI, which writes private state via
  providers.privateStateProvider.set).
- Long runs still need the detached pattern from the previous session:
      setsid bash -c '<cmd>' < /dev/null > /tmp/<log> 2>&1 &
  (a plain `&` inside a tool call dies with the tool's process group). Both
  the deploy and the e2e check were run this way.
- Both projects share one wallet/seed. Fine for testnet, but the two
  deployments are controlled by the same key.
